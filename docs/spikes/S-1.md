## 1. Objective & Hypothesis

Verify **H-1**: when a user initiates a file drag in Nemo 6.6.3 (or any GTK 3.24 X11 drag source) and Radivine maps a top-level `override_redirect = true`, 32-bit ARGB window with `XdndAware = 5` directly under the cursor mid-drag, the GTK3 drag source dynamically discovers the newly mapped overlay window and transitions its XDND session to it (`XdndEnter` → `XdndPosition` → `XdndStatus` → `XdndDrop` → `XdndFinished`).

Additionally, investigate:
1. Whether GTK 3.24.41 on X11 uses **managed DnD** (`gdkdnd-x11.c`) or **unmanaged DnD** (`gtkdnd.c`).
2. Whether GTK3 re-runs target-window discovery immediately on `MapWindow` (`pointer_nudge = false`) or waits for the next `MotionNotify`, and what happens if the user presses `Shift` over a Nemo folder and releases the mouse button **without moving the pointer**.
3. Whether GTK3 honors **unsolicited `XdndStatus` messages** sent while the pointer is completely stationary (e.g., when a submenu dwell timer or async enrichment completes without pointer movement).

## 2. Empirical Findings

### 2.1 GTK 3.24.41 Uses Managed X11 DnD (`gdkdnd-x11.c`)

Inspection of `/usr/lib/x86_64-linux-gnu/libgtk-3.so.0` and live X11 event traces confirmed:
- In `gtk_drag_begin_internal()` (`gtkdnd.c:1833`), `managed` is `TRUE` on X11.
- `gtk_drag_source_check_selection()` claims ownership of `XdndSelection` **synchronously inside `gtk_drag_begin_internal()`** (`gtkdnd.c:1901`), not lazily on first idle motion.
- `gdk_x11_drag_context_manage_dnd()` (`gdkdnd-x11.c:2945`) grabs the pointer via `gdk_seat_grab(..., GDK_SEAT_CAPABILITY_ALL_POINTING, ...)` and grabs only specific navigation keys (`Escape`, `Space`, `Return`, `KP_Enter`, `KP_Space`, `Up`, `Down`, `Left`, `Right`) via passive `XIGrabKeycode` on the root window—never grabbing `Shift_L` or `Shift_R`.
- On each pointer motion event (`gdk_dnd_handle_motion_event`), GTK3 walks the X11 window stack via `gdk_window_cache_get()` (which tracks `CreateNotify`, `ConfigureNotify`, `MapNotify`, `UnmapNotify`, and `DestroyNotify` on `root` via `SubstructureNotifyMask` + X SHAPE regions) and caches the current `dest_window`.

### 2.2 Critical Discovery: The Zero-Motion Hazard After `Shift` & Zero-Pixel `WarpPointer` Fix

While `gdkdnd-x11.c`'s `gdk_window_cache` updates its window list immediately upon receiving `MapNotify`, **GTK3 does not re-run `gdk_drag_find_window_for_screen()` on `MapNotify` alone**—it only re-evaluates the target window when it processes a `MotionNotify` (or modifier state change followed by motion).

We tested three `nudge` modes when `Shift` is pressed while dragging over an underlying GTK3 folder drop target and the mouse button is released **with zero subsequent pointer movement**:

| Mode | X11 Request After `MapWindow` | `map_to_enter_us` (Zero Pointer Motion) | Result When User Releases Button Immediately on Center Hub (Zero Motion) |
|---|---|---|---|
| `--nudge none` (`pointer_nudge = false`) | None | `XdndEnter` **never arrives** until pointer moves (`165,068 µs` when moved later) | **CRITICAL HAZARD:** Because `Shift` is held, GTK3 switches the underlying folder target to `GDK_ACTION_MOVE`. Releasing without moving drops onto the **underlying folder with `MOVE`** (`UNDERLYING_FOLDER_DROP: selected_action=['GDK_ACTION_MOVE']`, `GTK_SOURCE_DATA_DELETE_CALLED`)! |
| `--nudge zero` (0-px `WarpPointer`) | `WarpPointer(NONE, NONE, 0, 0, 0, 0, 0, 0)` | **`1,241 – 2,798 µs`** (`1.24 – 2.80 ms`) | **SAFE CANCEL:** X server synthesizes a `MotionNotify` at `(dx=0, dy=0)` without moving the cursor by even 1 px. GTK3 immediately sends `XdndLeave` to the underlying folder and `XdndEnter` + `XdndPosition` to Radivine. Center hub replies `XdndStatus(accept=false)`, so zero-motion release cancels safely (`GTK_CONTEXT_CANCEL: reason=no-target`). |
| `--nudge one-px` (`+1/-1` px `WarpPointer`) | `WarpPointer(..., 1, 0)` + `WarpPointer(..., -1, 0)` | **`1,164 µs`** (`1.16 ms`) | **SAFE CANCEL:** Also works, but requires two requests and momentarily displaces the pointer by 1 px. |

### 2.4 Timing-Related Unsolicited `XdndStatus` Without Pointer Movement

In `gdkdnd-x11.c` (`xdnd_status_filter`, lines 979–999), `context->action = xdnd_action_from_atom(display, action)` and `GDK_DRAG_STATUS` emission execute **unconditionally** upon receiving any `XdndStatus` `ClientMessage` from the current `drop_xid`, even when `drag_status == GDK_DRAG_STATUS_DRAG` (i.e., when no `XdndPosition` is outstanding and the pointer has not moved).

We verified both transitions empirically with **zero pointer movement** (`stationary_nudge = false`):
1. **`Reject -> Accept` while stationary (120 ms timer, zero pointer motion):** Sending an unsolicited `XdndStatus(accept=true, XdndActionPrivate)` immediately caused GTK3 to emit `GTK_CONTEXT_ACTION_CHANGED: dest_xid=0x7000003, action=['GDK_ACTION_COPY']`. Releasing the mouse button 180 ms later with **zero pointer movement** delivered `XDND_DROP` (`DROP_PAYLOAD_OK` in `1,093 µs`).
2. **`Accept -> Reject` while stationary (120 ms timer, zero pointer motion):** Sending an unsolicited `XdndStatus(accept=false, None)` immediately caused GTK3 to emit `GTK_CONTEXT_ACTION_CHANGED: dest_xid=0x7000003, action=[]`. Releasing the mouse button 180 ms later with **zero pointer movement** cancelled the drag at the source (`GTK_CONTEXT_CANCEL: reason=no-target`, `XDND_LEAVE`).

**Geometry Contradiction Identified in `WHEEL_ENGINE_DESIGN.md` (§4.1, §5.2, §6.2):**
With root `r_out = 116 lp` (`hit_radius = 128 lp`), child `r_c = 96 lp` (`hit_radius = 108 lp`), and `child_gap = 10 lp`, the center-to-center distance is `222 lp`. The child wheel's outer hit margin (`108 lp`) reaches `222 - 108 = 114 lp` from the root center—overlapping the outer `2 lp` of the **drawn** parent ring (`114..116 lp`) and the parent's hit margin (`116..128 lp`). Because §6.2 checks the deepest wheel first (`d <= hit_radius(child)` → `Bridge(child)`), opening a submenu via dwell or outer-band push while the pointer is at `r = 114..128 lp` on the parent segment would silently flip the hovered zone from `Item(root, k)` to `Bridge(child)` without pointer motion!
- **Resolution:** Update `WHEEL_ENGINE_DESIGN.md` §6.2 so a point inside a parent wheel's **drawn** ring (`d_parent <= r_out(parent)`) is never claimed by a child wheel's outer `hit_margin` (`r_out(child) < d_child <= hit_radius(child)`).

## 3. Verdict & Architectural Impact

- **Verdict:** **PASS** (`map_to_enter_us = 1.24–2.80 ms` vs. `< 50 ms` target).
- **Mandatory Architectural Update:** `pointer_nudge` must default to **`true`** using a 0-pixel `WarpPointer(NONE, NONE, 0, 0, 0, 0, 0, 0)` immediately after `MapWindow` (and after `UnmapWindow` when toggling off mid-drag).
