## 5. Accessibility review

Target: [WCAG 2.2 AA](https://www.w3.org/TR/WCAG22/), not certification. [Detailed results](media/W4/accessibility.json) cover every route in both themes plus both demo layouts in text, disabled, pending, image and result states. Pending inspection was extended only in the audit harness so axe actually inspected the pending state; normal timing remains covered by browser/reducer tests.

Keyboard tests cover skip-to-main, visible focus, mobile disclosure/Escape return, table and command scrolling, submenu focus transfer, disabled reasons, normal Tab exit, restart/cancel and state announcements. Compatibility uses a caption, scoped row/column headers and a named scroll region; mobile retains all columns and qualifications. The SVG duplicates the accessible action list and is hidden from accessibility APIs. Status regions are polite/atomic; pointer-frame updates do not flood them. Full-size buttons provide alternatives to dragging and tiny radial targets. Focused command regions now have valid names.

Computed semantic-token checks give a minimum **5.56:1** for measured text/surface pairs and **5.07:1** for focus/surface pairs, above the applicable 4.5:1 and 3:1 thresholds. These measurements cover the defined token combinations, not every composited pixel. Axe still requests contrast review for SVG/overlaid decoration and some controls, plus label-in-name review for the symbolic back arrow. Source/visual inspection confirms the arrow is a navigation symbol with the descriptive accessible name “Back to parent menu”; there is no conflicting visible word label. Token results and visible states support contrast, but pending manual review is retained rather than declaring every incomplete result resolved.

Browser-emulated forced colors, reduced motion and live preference changes remain usable. Reviewed forced-color and mobile screenshots show distinct controls, legible text and disabled reasons. Actual browser 200%/400% zoom, text-only enlargement, NVDA/Firefox or Chrome, VoiceOver/Safari, speech-control behavior and physical touch operation remain required. Automated DOM/live-region assertions do not establish what a screen reader actually speaks.
