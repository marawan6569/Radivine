# ADR-NW-001 — Optional concentric radial layout alongside Branching

**Status: Proposed.** Date: 2026-10-25. Intended registry number: ADR-045, subject
to availability. Target release: v0.3.0. Do not promote until implementation,
acceptance evidence and explicit owner acceptance. This file is the proposal;
`docs/DECISIONS.md` is intentionally unchanged during planning.

## Context

ADR-010 accepted adjacent wheels, parent-facing bridge sectors and a single open
chain. It rejected concentric rings because they compress labels, consume screen
space and obscure submenu depth. That decision remains valid and accepted for
the default Branching / Vine layout. PRODUCT_VISION now includes an optional
concentric layout on the roadmap. An alternative mode can address different
preferences without replacing or retroactively invalidating ADR-010.

## Decision proposed

Add `[wheel] layout = "branching" | "concentric"`, default Branching, selectable
in the Control Center and effective on the next activation. The same menu builder,
registry, action index, context enrichment and dispatcher serve both layouts.
Snapshot config/registry/input policy during a session. Do not remap an active
drag because its saved preference changed.

Concentric uses full-circle, equal-angle annuli sharing a fixed center, 60 lp
child thickness and 6 lp neutral gaps. Reserve configured depth and caption
space before mapping. A single central hub, persistent ancestor sectors, path
markers and breadcrumb communicate depth. Separate strict release targets from
hover hysteresis and transition grace. Use an enum and pure geometry/navigation
helpers, not strategy trait objects or a second action engine.

If all rings cannot fit at usable target sizes, choose Branching before the
session starts. Do not change the saved preference or switch during navigation.
The first version also falls back before mapping without a compositor. Preserve
existing platform limitations honestly. No scrolling, clipping of actions,
compressed replacement ancestors or dynamic center movement in this release.

## Addressing ADR-010's rejection reasons

| Original concern | Response and residual tradeoff |
|---|---|
| Cramped labels | Full circumference per level, fixed thickness, common breadth bounds, conservative content boxes, icons/ellipsis and caption. Extremely long labels still truncate; no tiny text. |
| Limited space | Explicit preflight reservation and whole-session Branching fallback. Small/high-scale screens may use Branching even for a shallow actual menu; supported and visible behavior. |
| Ambiguous depth | One annulus per open level, stable center/radii, path-marked parent, separate active ring, breadcrumb. All open ancestors stay visible. |
| Difficult pointer transitions | Whole-ring neutral gaps, bounded sibling adoption grace, independent strict release checks and new-geometry motion guard. No adjacent-wheel tangent triangle. |

Full-parent-slice fanouts were rejected because angular density compounds with
depth. Dynamic scrolling/paging was rejected for this release because it moves
action identities under a drag and would require a distinct navigation design.
Always recentering or shrinking was rejected for pointer predictability and
target size. A full strategy trait was rejected because two known layouts need
different small policies, not a runtime plugin architecture.

## Consequences and risks

- Larger concentric dirty areas may raise software raster/upload cost. Fixed
  geometry, no per-ring disc shadows, cached labels and analytic damage bounds
  mitigate cost; measured gates remain mandatory. Do not raise budgets silently.
- Center displacement can be greater than Branching. A neutral guided approach
  to the hub prevents accidental release; owner UX acceptance is required.
- Strict gaps can reject a near-boundary release that Branching would accept.
  This is explicit new-layout behavior. Existing Branching timing/hit semantics
  and visual baselines must remain unchanged.
- Shared Scene gains explicit visual kinds; existing renderer assumptions about
  child hubs/shadows must not leak into rings. Regression/golden tests are needed.
- Live reload needs active config/registry snapshots and stable provisional
  selection identity. Background jobs and conversion settings remain independent.
- One-monitor X11 capture, opt-in pass-through and opaque fallback limits remain.
  This ADR does not promise native-drop protection outside the overlay or after
  X-server/target-window loss. No MOVE or DELETE is ever generated by Radivine.

## Invariants and acceptance

ADR-002 (single overlay), ADR-006 (pure, time-injected Scene engine), ADR-009
(Private/no DELETE), ADR-012 (stable layout with live enablement) and the safe
default of ADR-016 are preserved. ADR-011 continues to govern Branching; the
concentric-specific policy is specified in [INTERACTION_DESIGN.md](INTERACTION_DESIGN.md).
Engine runtime dependencies remain std + smallvec and `forbid(unsafe_code)`;
renderer remains platform-independent with `forbid(unsafe_code)`.

Accept only after [TEST_MATRIX.md](TEST_MATRIX.md) automated, performance and real
Mint Cinnamon X11 gates pass, existing M1–M6/C1–C5 regressions pass, and the owner
accepts the N5 interaction/visual results. Rollback is selecting Branching for
subsequent sessions, or reverting focused unreleased feature commits through new
commits. Never rewrite released history or delete existing release assets.
